# 多 Agent 并行开发编排

## 触发条件

- 用户要求「并行启动多个 agent」「多 agent 开发」「分工实现」
- 一个项目有 ≥3 个可独立开发的模块，且已有（或可先产出）契约文档
- 单模块工作量小、模块间耦合低 —— 否则串行更快

## 铁律：先冻结契约，再并行

**没有冻结的契约就没有并行。** 开工前必须确认：

1. **数据模型文件**由单一 owner 独占（如 `types/index.ts`），其他 Agent 只读
2. **接口签名**（store 方法、组件 props、导出名）写死在契约文档里
3. **文件归属表**：每个文件只属于一个 Agent

契约一旦冻结，任何 Agent 不得私自增删字段。确需变更 → 先改文档，再改代码。

## 编排步骤

### 1. 先摸清"接线点"

启动 Agent 前，自己读一遍：
- 主入口文件（`App.tsx` 等）**已经 import 了哪些导出名** —— Agent 必须保持这些名字，否则主入口编译不过
- 现有 store / lib 的**真实签名**（不是文档里的，是代码里的）
- 每个待实现文件的当前状态（占位内容）

这些信息必须**原样写进 Agent 的 prompt**，不能让 Agent 自己猜。

### 2. 依赖缺口要在本批补齐

例：A3 的节点详情要嵌 A4 的组件，但 A4 属于上一批且没做。
→ 把 A4 一起启动，并在两边 prompt 里写死同一个 props 契约。
→ 明确告知：「A4 正在并行实现 X，你直接按此契约 import，**不要自己实现一份**，也不要等它。」

### 3. 批次按依赖图调度

```
无依赖的模块 ──┬─→ 依赖它们的模块
              └─→ ...
```

同一批次可全并行；跨批次必须等。**关键路径上的模块优先启动。**

### 4. Agent prompt 必含要素

| 要素 | 说明 |
|---|---|
| 必读文件清单 | 契约文档 + 视觉参考 + 现有样式文件，让它自己读，别把内容抄进 prompt |
| 交付物 | 精确到文件路径 + **必须保持的导出名** |
| 铁律 | 文件独占 + 契约冻结 + 不复制实体，逐条写死 |
| 可用接口 | 真实签名，含 import 路径 |
| 并行契约 | 兄弟 Agent 正在做什么、你要按什么签名调用它 |
| 设计约束 | 变量/色值来源、禁用项（emoji、硬编码色值） |
| 验收方式 | 具体命令 + **并行环境的容错说明** |
| 报告要求 | 限定字数，要求列出「改了哪些文件 / 验收结果 / 需要别人配合什么」 |

**并行环境容错必须写**：`tsc` 会报出其他 Agent 写了一半的文件的错。
明确告诉它：「只关心与你文件相关的错误，别人的错误忽略，**更不要改别人的文件去消除错误**。」

### 5. 子 Agent 只做 SSR 验证是不够的

子 Agent 能跑的是纯逻辑断言 + `react-dom/server` 渲染。
**它验证不了**：IndexedDB、外部 SDK、真实点击、滚动、z-index 遮挡、卸载清理。

→ **编排者必须在全部 Agent 返回后，自己跑一次真实浏览器端到端**。
→ 这一步是发现真 bug 的主要来源，不要省。

## 统一验收（三层，缺一不可）

```bash
# 1. 类型 + 构建（每次必跑）
npm run build          # 或 npx tsc --noEmit && vite build

# 2. 纯逻辑 / 组件 SSR 断言（无测试框架时）
./node_modules/.bin/esbuild <tmp>.tsx --bundle --platform=node --format=cjs \
  --jsx=automatic --loader:.css=empty --outfile=/tmp/v.cjs && node /tmp/v.cjs

# 3. 真实浏览器端到端（编排者跑，不是子 Agent）
agent-browser open http://localhost:5173/
agent-browser snapshot -i        # 拿元素 ref
agent-browser click @e5
agent-browser eval '<js>'        # 读状态 / 直接派发事件
agent-browser screenshot
agent-browser console            # 看 React 崩溃错误
agent-browser close              # 必须关，否则留僵尸进程
```

**端到端要覆盖**：核心闭环（建 → 填 → 存 → 显示）、跨模块联动（改 A 处，B 处是否跟着变）、
每个 tab 都切一遍、卸载重挂载、外部 SDK 失败时的降级路径。

## 编排者必查的 5 件事

Agent 的自我报告**不等于事实**，逐条核实：

1. **越界改动**：`git status` 或按归属表核对每个被改文件 —— Agent 常会"顺手"改主入口完成接线，
   结果可能是对的，但流程违规，必须知情
2. **契约是否真被遵守**：grep 兄弟模块的 import，确认它真的用了对方组件而不是自己重写一份
3. **死代码**：Agent 可能建了文件但没接线。发现只提不删
4. **全局声明的归属**：`*.css` 等全局类型声明不能挂在某个 feature 目录下（该 feature 一重构就全崩）
5. **生产产物合规**：明文密钥、演示/测试数据、被禁的第三方源，都要在 `dist/` 里搜一遍确认没有

## 实战踩坑清单

- **并行跑 build 会互相干扰**：让子 Agent 只用 `tsc --noEmit`，最终 build 由编排者统一跑
- **本环境 shell 的 `grep` 对中文/多字节不可靠**（静默无输出）→ 一律用 Grep 工具
- **`agent-browser click` 是真实鼠标点击**：元素滚出视口或被遮挡时**静默失败**（返回 ✓ Done 但没生效）。
  用 `eval` 直接 `.click()` 区分「应用真有问题」和「点击落空」
- **SSR 下 zustand 快照固定为 initial state**：想验证 store 驱动的渲染，得先钉定快照或改用浏览器
- **外部 SDK 的调用点全要包 try/catch**：SDK 在鉴权失败/上下文丢失时抛错，冒到 React 里会白屏，
  一个可选模块能拖垮整个应用
- **卸载清理阶段绝不能抛**：`destroy()` 抛错会打崩整棵树，这类 bug 只在"切走再切回"时出现

## 交付报告该写什么

给用户的报告里要区分三类，别混为一谈：

1. **Agent 交付了什么**（文件 + 验收结果）
2. **你（编排者）验证时发现了什么**（越界、死代码、真实 bug）
3. **你修了什么、为什么修**（尤其是自己上一轮的疏漏，直说）

不要只转述 Agent 的自我报告。
